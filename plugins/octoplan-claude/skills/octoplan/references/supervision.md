# Supervised delivery

Load this after the user's delivery go on a finished plan, or when resuming a stream whose recorded go still stands. From here on this session is the **supervisor**: it does not write the deliverables, it sequences the plan, sends each task to a fresh worker, checks the proof that comes back, and stops where the contract says a person decides.

## The mandate comes from Octopad

Re-read the delivery contract's Decisions on the stream before the first task and after any interruption: the delivery mode (named in the go Decision), the reviewer routing, the stacking choice, the gate map, the stakes Decision with the stream's kill question, and the recorded go. Those Decisions are the mandate. The go names the reviewed graph (every task's stable ID, its rank where it has one — human-only tasks included — and its last-edit timestamp). Compare both directions: a task edited after its timestamp or absent from the record was never reviewed or shown to the user, and a recorded task missing from the current graph is the same drift in reverse — route it through the skill's Replanning rules (focused re-review, and consent where its effects were not disclosed) before working it. When that re-review passes, update the go record's graph snapshot for exactly those tasks — a guarded edit that touches nothing else in the record — so the drift check clears instead of firing forever.

**Local versus remote is never what decides autonomy — the disclosed list and the written waits are.** A disclosed remote effect — a migration to apply, an infrastructure setting, a deploy — is as authorized by the go as a local edit, under the same floor as everything else: the target's own rule files win, and a person the house rules name is waited for in every mode. And what stops a remote step is exactly what stops any step: an effect the disclosed list never carried, a target or class of work the approved plan never named (SKILL.md, Replanning), a wait with a written source — a dependency edge not yet done, a human-only task, a gate in the contract, or the stacking choice set to wait — or, under checkpoints and step-by-step, its marked point.

**The delivery mode sets when the user is interrupted — never what is checked:**
- **Full autonomy** — the go authorized every effect the plan disclosed, protected ones included. Land each change once its gates pass, resolve what you safely can alone and report it afterwards, and interrupt the user only for: an undisclosed event — a protected effect missing from the go Decision's disclosed list, a changed outcome, or an authority need the plan never named (new consent for a new fact, stated as its consequence) — a person-wait — a point the gate map's person-wait class or the target's own rules route to a named person — or a failure that survives the retry rules below. Progress flows as reports, not questions.
- **Checkpoints** — full autonomy, plus a pause at every marked point: the bold lines copied into the go Decision — human steps, protected effects, landings. Report the state there and wait for the user before continuing that branch.
- **Step-by-step** — report after every task and wait for the user before the next.

Nothing agreed only in the chat counts, and nothing remembered from the planning conversation counts either — if it matters and it is not recorded, ask again and record it. A go that exists only as a clause inside another Decision is not the recorded go: look for it as its own Decision, and if it is not there, there is none — ask.

**Every resume and every takeover re-answers two things before the first dispatch, and faithful continuation is not an answer to either.** First, the stream's kill question and its proportion: does the plan still lead to the outcome, and is what the run has spent so far still proportionate to the decision it feeds? A fresh supervisor is the cheapest place in the whole system to catch a runaway, and the inherited framing — the go record, the predecessor's reports — is the record of a run, never evidence the run still makes sense. (A stream planned under an earlier skill version may lack the stakes Decision or a countable definition of success — create both on resume, per the resume rules in SKILL.md, before applying the rules that read them.) Second, **any diagnosis inherited from a predecessor is unverified on this leg until its own proof is re-run**: name the diagnosis you inherited, name the observation that proved it, and reproduce that observation on the current artifacts before dispatching anything that depends on it. This is most binding exactly where it feels least necessary — a root cause recently found, fixed and verified reads as tested ground, and that reading is how a repaired defect's siblings survive: the repair of one instance is not the closure of the class (the parity rule in `references/planning.md`, step 6, names the class for rigs). Write both answers, one line each, on the stream or the task you resume with. And reconcile the run's live state before the first dispatch: standing authority (the go and what it covers), pending protected effects, workers still in flight, and open person-waits — a handover is evidence of a run, not a verdict that its shape may continue.

The target's own rule files stay the floor. Where they and the delivery mode disagree, the rule files win — a person the house rules name is waited for in every mode.

On a multi-stream effort, load `references/multi-stream.md` now and read the effort's Blueprint page, before the first task and after any interruption — together they carry the effort's shape, the shared-landing order, and the cross-stream rules. Your stream is your whole territory: rebalance only it, and stop for the user on anything touching a seam.

## The delivery report — one page, updated in place

The report page is for runs the user follows closely: create it when the mode is checkpoints or step-by-step, or the stream has more than 5 executable tasks. On a small full-autonomy run, skip it — the task graph and the chat lines (loop step 5) already carry everything, and the closing recap tells the whole story. When it applies: before the first task (or on resume, when none exists yet), create ONE page on the stream named `Delivery report — <stream>`. It opens with the position-and-outcome line — task N of M, the current phase, and the definition of success's number with its current value, updated at every event — then the phase map: the delivery steps in order, each phase's tasks under it with their titles in plain words, and every step a person performs in bold with its owner — followed by one state line per task and an open "needs you" list. On a stream of three or four tasks the phase map and the state lines are the same short list; keep it to that rather than inventing phases. This page is what the user follows for the whole run: the aggregate of everything worth reporting, centralized so nothing gets lost in chat. It is written for the user, so the skill's Plain words rule applies to it, and it opens — like every chat report and escalation during delivery — under the Delivery banner (SKILL.md, One program).

**The report is a view, never the record.** It holds no fact the task graph does not; Octopad's task states and comments are what a resuming session reads, and where the two disagree the tasks win. On resume, rebuild the state lines from the tasks before showing the page to anyone. Update it in place at every event: edit the existing lines, never append a fresh narrative under stale text — each edit follows a fact you just verified or an agent's return you just read. States use one vocabulary, never a bare "done": **built → reviewed → merged → applied → verified → released → accepted**, stopping wherever the stream's finish line actually is, or the domain's equivalent (drafted → reviewed → approved → published). A replan rewrites the phase map in place, per the skill's Replanning rules.

## The loop

Repeat until the stream is done or nothing is left that the mandate lets you touch:

1. **Pick.** Take the next task Octopad reports as ready — dependencies done, nobody else's assignment, not blocked. **The graph is the only judge of waiting: ready means work it now.** The only stops that override a ready task are the two in Stop conditions below — an observation answering the kill question, and a shared-infrastructure distress signal, each recorded on the stream. Never add any other wait of your own on top of what Octopad reports — dependent code sitting on an unmerged branch is the stacking rule's normal case (see Delivering the work), not a reason to hold the task; the real waits all have a written source, as a dependency edge not yet done, a human-only task, a gate in the contract, or the contract's stacking choice set to wait for the base to land. One exception you resolve at pick time: a ready task whose Preconditions name a state that is not live yet and that only a person can make true (a migration applied, a deploy) is a plan defect — the planner should have wired that wait as a human-only task with an edge; wire it now, per Replanning, and proceed on whatever is actually ready. A task whose What carries "Octoplan flesh-out required" is a placeholder: never send it to a worker, stop and tell the user it needs a planning pass first. Otherwise set the task in progress — or, for a group the plan marked independent, take the whole group and set each member in progress (see Running workers in parallel); steps 3–5 then run per task as each returns.
2. **Send.** Launch a fresh worker subagent with the template below. One task per worker, always.
3. **Collect.** The worker does the one job, writes what it did, what it decided and anything it hit onto the task, and returns a one-line status. Treat the one-liner as a signal only: the task is the record.
4. **Check.** Run the verification gate below. Only then close the task.
5. **Report.** Update the delivery report where one exists, then post to the user at most one plain line per event since the last report — even under full autonomy; silence is not a progress report. Name the state, never a bare "done": built, reviewed, merged, applied, verified, released, accepted — stopping where the stream's finish line is. **Every report also carries the position-and-outcome line: where the run stands in the plan — task N of M executable tasks (N the `#N` rank), and the phase from the phase map where one exists — plus the definition of success's number and its current value, in the stream's own units** — "task 4 of 11 · rig build · 3 of 16 comparisons run" — because delivery is the longest stage the user watches, per-event reporting can be accurate for hours while the deliverable never moves, and this one line is what makes both invisible states impossible to miss. Once that number has moved at least once, two consecutive closes that move it by nothing get a written line at the next kill-question check: what the base is being deepened for, and when the number moves next — a run that only deepens its base is drifting, and foundations are not progress the definition of success can see. Where the stream's output is observed behaviour — an agent under test, a user flow, anything scored — **quote one verbatim line of what the observed system actually did or said, per arm or per run, not only its score**: the user holds domain knowledge no supervisor has, the report is the only surface that knowledge can attack, and "the arm answered 'the workspace is empty' and made no tool call" invites the question that "2 of 8" never will. No inner monologue: what was verified, not how you reasoned about it. One thing never compresses: a call you made that the user could reasonably disagree with — a finding you dismissed, an item you decided was yours or theirs, a deviation from the plan — gets its own line in chat when you make it. Review findings live on the task — the top one may get one line in chat, never a narration. Every blocker you name says what it stops and what keeps moving. A standing blocker is named once, then lives on the report; repeat it in chat only when its state changes or it comes to block everything. When you repeat a task's precondition, carry its reason. When you hand a person a task, say it already holds everything they need and name where it sits. And when the user challenges a finding you reported, re-read its primary source before defending it — retracting is cheap while a worker is still running and expensive after.
6. **Advance.** Move to the next ready task, or stop at a gate.

## Stop conditions and the outward check

**An observation that answers the kill question stops the run — whoever made it, whenever it was written.** When any record of this run — your own comment, a worker's report, a reviewer's finding — states a fact that contradicts the stream's definition of success or answers its kill question, that fact is a stop condition for the WHOLE stream — unless you can name in writing a branch whose value does not depend on the assumption just answered, in which case only the dependent branches stop — and it is never material for prose. The four ways supervisors have neutralized such a fact, each in writing, are the same failure in four shapes: dispatching more work onto it, deferring it to a later task's scope ("the verdict task will name it"), recording it as a stated limit, and declaring an uneliminable difference to be the design — a declared difference in an experiment is a defect with better manners. A fact answering the kill question always trips the Replanning limit — the stream's logic is broken, so this is a fresh Octoplan pass, not a rebalance: stop, and put the fact to the user in the six-field report. The one exception a supervisor may take alone: eliminate the fact itself, immediately and verifiably, before any further dispatch.

**A distress signal from shared infrastructure stops that branch — it is never a nuisance to route around.** Timeouts, connection failures, or saturation warnings from a resource other work depends on (a shared database, a rate-limited service) pause every task that loads that resource until the cause is understood and written on the stream. Telling a worker to expect the errors and press on is how a shared outage gets built by instruction. Where a worker failure carries this signal, the retry-by-failure-class rule yields to this one: write the distress on the stream first — that record is the wait's written source — and only then may a reduced retry run, as a diagnostic after the cause is written, never before.

**Every third task close — and always at the close before the final validation task, and at every handover: re-ask the stream's kill question, in writing.** One line on the task just closed — the kill question, and what this leg has actually observed that answers it — plus one line on cost: what verification has spent against the stakes record since the last check, dropping in writing any check that has outgrown the decision it protects. The loop's own questions all point inward (did this task's checks pass); these are the two that point outward (does the whole run still make sense, and is it still worth its price), and without a fixed cadence nobody inside the loop ever owns them — a supervisor who never stops to think is otherwise doing the job as specified. Two sentences, and they are the only check that catches a runaway from inside.

## Run discipline

**Say a thing exists only once the call that created it has returned, and name what came back.** A reviewer, a worker, a task, a Decision, a message: until then you have an intention, not a fact. Nothing you have not seen return goes into a report — the user cannot see the work, so your account is its only witness, and an intention told as a fact is the one failure this design cannot absorb.

Workers in this mode do NOT emit the task's continuation block — you own the sequencing. The Next lines exist for the manual fallback.

Keep your own context small. You read task comments and gate results, not the workers' working history.

**One supervisor at a time, recorded.** On the go and on every resume, read the go Decision's supervisor line FIRST. Empty, or naming this session → update it (guarded by its `expected_updated_at`) to this session and continue; a guard conflict means someone wrote meanwhile — re-read, never race. Naming another session → that session owns the stream: take over only on positive evidence it stopped — the user saying so, or the platform showing its session ended. A recent write proves the predecessor is ALIVE, and no timestamp ever proves it stopped. The takeover write carries the same `expected_updated_at` guard, recording the evidence in the line; on conflict, re-read the whole Decision and re-evaluate ownership and the stop evidence before doing anything. The line cuts both ways: re-read it before every worker launch and every task close, and if it no longer names this session, stop instantly — the stream has a new supervisor.

**A worker that fails is retried by failure class.** A worker that RETURNED work you cannot verify is retried ONCE with a fresh worker; if the second also returns unverifiable work, stop that branch and escalate with the six-field report — never finish the task yourself, whatever the mode says. A worker that NEVER RETURNED — an error, a stall, a killed session — is an environment signal, not a task signal: first re-read the task for fresh writes (a worker still writing is alive — wait, don't duplicate it), then say so in one line, retry once with the run reduced (one worker at a time), and escalate only if a third dies. A user-directed attempt is one attempt, not a standing licence.

## The worker launch template

**Dispatch by lane where lanes exist.** When the environment defines one agent per rubric lane (an agent definition pinning model and reasoning depth together, e.g. under `.claude/agents/` — a one-time team setup; check for them before the first task), launch the worker or reviewer AS the lane agent matching its saved route — model and depth are then both enforced by the definition, and the template's depth line reads `pinned by your lane definition`. Where no lanes exist, or a saved route has no matching lane, pass the model on the launch call, keep the template's request wording (`requested, not enforced: this launch call cannot set it — run at it if you can; if you cannot, say so in your status line`), and say once at the start of the run, not per task, that depth is then a request nothing verifies.

Send this, with the real names filled in. Nothing else: beyond it, the worker briefs itself from Octopad and from the environment it already has.

phrasings from the lane paragraph above this template>

## Verification gate — before any task is closed

- **The task's Verify steps run for real, and their real output lands on the task.** Whoever runs them — the worker, or you when a step needs your access — the output is pasted into the task before the close. A claim that checks passed is not evidence. No output on the task, no close. One deliberately failing run is expected where the Verify slot carries the call-site proof: read the pair, not the last output. Where the change touched a production path and the task's Verify slot carries no call-site proof, add one before you close — a suite green with the real path removed is not evidence — unless the task's Verify slot says in one line that the call-site proof was deliberately omitted on the stakes Decision's reversible-and-internal record — a plan that subtracted rigour visibly, on the record it is entitled to read, is honored, not overruled. A silent absence is not a downsizing: add the proof.
- **Honor the task's Review line.** When it says required, YOU spawn the reviewer subagents — fresh, none of them the author of the work, each at the Review line's route, by lane where lanes exist — to attack the finished change against the real sources, worst problems first. Load `references/routing.md` and run the lenses the Review line names by it — the premise lens is mandatory there whenever the task's output is a measurement, comparison, score, or verdict, whatever the Review line says; you may add one, and drop one only for a re-review narrower than the round before, naming which and why on the task. The worker never spawns its own reviewer. Confirmed findings go back to a worker, get fixed, and are re-verified before the close.
- **Two finding-bearing rounds is one task's review budget.** Each round can be individually justified — every finding real, every fix bought — and the rounds collectively be the failure; nothing inside a round can see that, so the budget lives here. From round two on, every reviewer's mandate includes one sentence of convergence judgment: whether another round of the same kind would reach the remaining finding class, or the surface is just moving. Before any third round on the same task, stop and choose in writing on the task — the remaining finding class becomes a stated, recorded limit of the deliverable; or the task is re-planned (Replanning); or the user decides. Escalating a pattern is a first-class move, not something to invent under pressure.
- **Every finding gets a disposition before the next round — after one test: does it answer the stream's kill question?** A finding that does takes no disposition at all — it is a stop (the kill-question rule above), and neither "defer" nor "stated limit" can hold it. Every other finding from the round — blocking or not — is marked fix now, defer with its reason, or dismiss with the evidence; the re-review prompt lists whatever was deferred, and a finding still deferred when the task closes is named in the closing comment with who owns it next. A finding left off the list is how a known defect crosses a round unfixed and comes back blocking.
- **A parity-defect fix does not close without the class.** A task closing the repair of any parity defect (a difference between a rig and the real system it stands in for) carries the full outward-in parity manifest (`references/planning.md`, step 6, validity half) on the task or a linked page.
- **An expensive run does not dispatch before its rehearsal, and a failed rehearsal does not dispatch at all.** Where a task's Verify slot carries a rehearsal item, its result is run and reported — pass condition stated in advance — before the full run is dispatched; a plan that should carry one and does not is a plan defect to wire now, per Replanning. A rehearsal that failed its stated pass condition stops the branch and routes through Replanning and the six-field report; reporting a failed rehearsal is not clearing it.
- **Read the dependencies' deferrals before the close.** Check the specs of the tasks this one depends on for any deferral naming it ("X is handled by this task"); an unhonoured deferral is a blocking finding here, not the next task's problem.
- **Machine review always runs; human routing decides who ALSO clears it.** The contract's reviewer routing names the person for a class of task; that person's clearance is added on top of the fresh review, never instead of it.
- **One comment of yours on the task before it closes:** name the reviewer you spawned and what it returned, what the gate found, any retry it took, anything you decided along the way, and anything the job revealed about how this delivery is going. Size it to Octopad's comment limit; detail that will not fit goes on a page linked to the task — never into the task description, which is the plan's spec — not a second try at the same comment; and reasoning is never deleted to fit a field — the page-and-pointer form exists for exactly that. **A review round's record or an authorization is never overwritten:** a later round or a superseding Decision points at its predecessor, which keeps its reviewer, findings, evidence, and timestamps — a one-line "superseded" note in place of the old body destroys the only trail that shows how a wrong answer was reached. Two guarded fields are exempt because they record who is acting, not what was authorized: the go record's graph snapshot (updated after a re-review passes) and its supervisor line. For a number that later work will move, point at the authoritative file instead of copying the figure — a copied number in a comment goes stale silently. Also record any outward notification you sent or deliberately skipped (a review handoff, a message to the person the routing names), and read that record before sending or skipping one — supervision changes hands, and a duplicate handoff and a missing one both cost. No comment, no close. The task is what a later session reads; a run whose record lives only in your chat is a run nobody can reconstruct, and nobody can improve.
- The delivery mode can remove a human's waiting time. It can never remove a check.

If a Verify step turns out to be unrunnable, that is a blocker, not a licence to skip it.

## Delivering the work

- **One task, one branch.** The worker branches from the current base, does its job, and opens the change for review when the target's process uses pull requests. Follow the target's rules for how a change is named, described and checked; read them, do not assume them.
- **Landing under full autonomy:** once every gate for that task has passed — checks green, fresh review clean, any person the house rules route cleared it — land it and record that on the task.
- **Before you land any protected effect, re-check the permission at the moment of the act.** Re-read the current task spec, the go record it must still fall inside, and the contract Decisions, against the exact change being landed: all three must still permit exactly this effect. A mismatch — a spec superseded in comments but never rewritten, an effect class the go never carried — stops the effect and routes through Replanning; no comment, and no memory of an earlier check, waives this.
- **Landing under checkpoints or step-by-step:** a change whose landing sits at a marked checkpoint (or, step-by-step, every change) waits. Report it, name who has to clear it, and move on to independent work.
- **Stacking on:** a dependent change branches off the open change it needs and targets it; when the base lands, retarget it to the main line. **Stacking off:** the dependent task waits for the base to land. Either way, **a base that moves under you is a replan trigger you own** — no worker will report it: re-read what every open change actually sits on, write the new landing order onto the stream, and run the skill's Replanning rules before sending the next task.
- **Wording a worker invented is new scope.** Where a later task is scoped to write or rewrite wording a user will read, no earlier task should have written any, so a worker that had to is reporting a miss in the plan, not a detail. Copy each string it recorded into that task's How before it launches, then run the per-task self-check on the task you changed. If that task has already started or closed, stop and run the skill's Replanning rules instead: a copy pass cannot settle text it never saw.

## Running workers in parallel

Only for tasks the plan itself marked independent, never more of them at once than the plan marked, and each in its own isolated checkout so two workers never write the same file. Where the environment runs subagents in the background and reports each completion, launch the marked group together and run the verification gate per task as each returns — the gate never runs in bulk. Group failures split by the ordinary failure classes: a member returning unverifiable work is retried alone while its siblings continue; a member that never returns is an environment signal — stop launching new members, let the in-flight ones land, then retry it with the run reduced. Never in parallel: data migrations, shared generated artifacts, anything one sibling shapes for another. When in doubt, run them one at a time — sequential is the default, parallel is the exception.

## When the plan changes mid-delivery

A worker that discovers something the plan got wrong stops and reports it instead of improvising. Run the skill's Replanning rules (SKILL.md) on the whole plan, then resume the loop on the corrected order — they carry the consent rule for out-of-mandate work and the line past which the stream needs a fresh planning pass instead of a patch.

**The user changing the mandate mid-delivery is the same trigger:** run the two sweeps the Replanning rules name (SKILL.md) — the open specs, and the retired Decisions' artifacts — before your next dispatch. Recording the change as a Decision and applying it to the tasks in flight is only the visible half.

## When to stop, and how

Stop for a human when the gate map's person-wait class says so, when the delivery mode's rules above say so — a marked checkpoint, every task in step-by-step, or new consent needed — or when a problem survives the retry above. Then report in the user's language, in plain words per the skill's Non-negotiables, under the Delivery banner, six fields, nothing else:

**State** — where the stream stands. **Done** — what is finished and proven. **Blocked** — what is stuck and why. **Decision expected** — the exact call you need from the user. **To unblock** — what has to happen, and by whom. **Next step** — what resumes the moment it clears.

Any field can be "none". Keep each to a line.

Before telling the user that nothing can proceed, walk the open tasks and name, per task, the written source of its wait — a dependency edge not yet done, a human-only task, a gate, the stacking choice set to wait. A wait that exists nowhere but in your own reasoning is not a blocker: it is either work (a ready task, sent to a worker now) or a plan defect (a real-world wait the graph never carried — wire it, per Replanning). A stream that idles while ready tasks sit on the board is the supervisor failing, not the stream waiting.

**A checkpoint blocks only its own branch.** Everything independent and safe keeps running while a person decides. Stop the whole stream only when nothing safe is left to do.

**A decision is only escalated when it is actually the user's.** Before putting any call to them, run both parts of the ownership test: (a) does the call change something the user owns — money, data, publication, a commitment to someone else, their own time; (b) could a defensible option, chosen wrong, leave the work unusable? Unless (a) is yes, the call is yours: decide, record it and its reason on the task, and report it in one line the user can override. A technical design choice that is reversible and internal never goes to a non-technical user, however unsure you are — uncertainty routes to a reviewer or a recorded Decision, not to the person who cannot read the code. And an escalation is asked ONCE: a "Decision expected" line standing unchanged across three consecutive task closes, or four hours of wall clock with no state change, is no longer an escalation but a stall you own — re-run the ownership test and decide, or route the question through Replanning; re-serving it is not progress. This never reaches a wait with a written source — a marked checkpoint, a gate-map person-wait, or consent for an effect the go never disclosed: those are waits, named once and living on the report, and the stall rule fires only on a question that fails the ownership test or has no written source for its wait. And the mirror rule for waiting: **a dependency edge blocks only what its stated purpose actually protects** — before parking a ready-adjacent task behind an open one, name what the edge exists to guarantee and check whether it is already guaranteed; an edge whose purpose is already satisfied is a plan artifact, not a wait.

**Verify before you escalate.** Before naming an item as a person's, verify the claim that makes it human-only against the live environment, this session — a claim inherited from a task description, a worker comment, or a prior session's report is not evidence, and a false one hands the user work an agent could do. If the claim is false, do not work a human-only task yourself: report it as a plan defect and run the skill's Replanning rules to re-spec it as executable. A reversible action inside the plan is done, then reported — never reported as a risk for someone else to do. This never widens the gate map or anything the target's rule files reserve for a person: a person-wait stops for its named human even when you could technically do the work.

## Recovery and handover

The state is Octopad: the contract Decisions, the recorded go, each task's status, and each task's comments. Nothing about this run lives ONLY anywhere else, which is what makes it survivable — the delivery report is a view rebuilt from this state, never a source of it.

If this session dies, a fresh one resumes by invoking the skill on the stream: it sees the recorded go, comes straight back here, re-reads the contract Decisions, the open tasks and their comments, rebuilds the delivery report's state lines from them, and picks the loop back up (rebuilding the report only where one exists or applies). If your own context is running low, hand the rest of the stream to a fresh supervisor before your judgement thins, rather than pushing on and stalling in the middle of a task. ## Delegating the run

Delegation needs three things from the environment: this session can spawn a subagent, that subagent can itself spawn subagents (its workers and reviewers), and it can be messaged again after it reports (so the user's decisions reach it at gates). Where any of the three is missing, this section is unavailable — hand off with the block instead.

Spawn ONE sub-supervisor subagent — fresh, never a fork, because a fork inherits this session's full conversation, spent budget included, which is the problem being escaped — at the supervisor route recorded in the go Decision, by lane where lanes exist, never substituting the model. Open its prompt with the two lines of the supervisor handoff block (`Octoplan <work stream>` plus the Octopad address line), so it invokes this skill and briefs itself from Octopad exactly as a pasted block would: the recorded go, the contract Decisions, the open tasks and their comments. Under those two lines add only what is true of the environment and held nowhere in Octopad — the branch the chain stacks on, and nothing more: the task in flight was closed out or parked with its state written on it before delegating, like any handover. Every rule in this file binds the sub-supervisor as if it were the supervisor, with one exception: it never delegates — when its own context thins it reports that like any other state, and the relay retires it and spawns its replacement the same way.

From the spawn on, this session is a relay, nothing more. It announces the delegation to the user in one line, forwards the sub-supervisor's reports and six-field escalations VERBATIM — a relay that summarizes an escalation weakens every gate it passes — and carries the user's decisions back, adding no judgment of its own, so it barely grows. One level of supervision only: the sub-supervisor spawns workers and reviewers like any supervisor and never another supervisor; the relay alone spawns sub-supervisors. A sub-supervisor that never returns is an environment signal: say so in one line, re-spawn once with the same prompt — the state is Octopad, so nothing is lost — and escalate with the six fields if the second dies too. A relay whose OWN context thins retires its sub-supervisor at a task boundary first, then hands off with the ordinary block — never two supervisors alive on one stream. The sub-supervisor is a child of this session: if the relay dies, it dies with it, and recovery is unchanged — a fresh session invoking the skill on the stream resumes from Octopad.
