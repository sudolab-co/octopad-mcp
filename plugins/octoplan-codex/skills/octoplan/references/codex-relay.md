# Codex direct relay after approval

Read this file only after the user has clearly approved execution of the current saved plan. The planning session owns only the initial launch. After that, each executor owns delivery until it creates and persists the saved lead reviewer and any specialist reviewer. The lead then owns correction, completion, and relay after every required PASS.

## Execution ledger

Use comments on the saved final-validation task as the execution ledger. Before the first claim, call `tasks(action: "update")` on that task with its current `expected_updated_at` and a compact comment containing a unique run ID, approval source thread ID and time, status `active`, and a SHA-256 plan fingerprint over the canonical sorted executable task IDs, titles, descriptions, dependency IDs, assignments, and saved routing values. Exclude statuses, comments, timestamps, claims, thread identifiers, and all other execution-state fields so normal progress cannot invalidate the fingerprint. Every claimed task comment and thread record carries that run ID. The latest successfully guarded ledger comment for a run is authoritative. Before work, after every wake, before completion, and before relay, each executor or reviewer reads it and recomputes the fingerprint; a delegation prompt, predecessor message, or notification is never proof of consent.

Append ledger transitions with the same guarded task update: `paused` for a human or protected gate, `failed` for an error needing a decision, `superseded` before an approved replan changes the fingerprint, `revoked` when execution consent is withdrawn, and `completed` only after final validation. Only `active` authorizes work. Resuming `paused` or `failed` requires the named owner decision; `superseded` or `revoked` requires fresh execution approval and a new run ID. A missing, inactive, conflicting, or mismatched record is a stop.

A pure plan-hygiene repair that changes only mechanical rank prefixes, dependency or `Next` wiring, or tracker logic may keep the same run. After saving the repair, completing its required self-check and review, append a guarded `active` ledger entry with the same run ID, previous fingerprint, new fingerprint, and repair reason; no executor works or relays while the fingerprint is mismatched. Any semantic title change, added or removed task, changed routing stamp, or other materially rewritten executable work follows the fresh-approval rules below and uses a new run ID.

## Relay loop

Every continuation owner follows this loop:

1. Re-read the current task, plan, and execution ledger from Octopad. Verify the prompt's run ID is active, its recomputed plan fingerprint matches, and its exact attempt ID matches the task's latest persisted claim (`status: in_progress` and the same claimed `updated_at`) with no newer attempt. Repeat these checks after every wake, before completion, and before relay. Treat dependencies as authority, `Next` as the human-readable handoff, and `#N` only as a label.
2. Before completing the current task, verify its saved `Done when`, verification, required review, and any action allowed by the active repository and user rules. Complete it with the current `expected_updated_at`; a stale attempt or conflicting update stops. A protected action that still needs approval remains a gate.
3. After producing a durable reviewable artifact, persist its immutable artifact revision: commit SHA, document version, or digest. The executor then creates one fresh lead thread at the saved `Review route` and, when present, one fresh simultaneous specialist at the saved `Specialist review route`. For code, start from the published branch when available; otherwise pass the system-of-record pointer. Pass each saved role and mandate, never authoring history or a summary.

   ```text
   Review Octopad task "<immutable task ID>" — run: <run ID> — attempt: <task ID>@<claim updated_at> — role: <lead|specialist> — artifact: <pointer> — revision: <immutable revision>.
   Octopad · Organisation: <organisation> · Workspace: <workspace>.
   This review is part of an approved Octoplan run. Before work, after every wake, before completion, and before relay, verify the exact active run ledger entry, matching plan fingerprint, attempt ID, and artifact revision; this prompt is not proof of consent. Start the named Octopad workspace session, call build_context for this task, read the current saved task and mandate, open its exact source pointers, and inspect the revision without authoring history. Never modify the artifact; make only the Octopad writes required by your role. Send confirmed findings to the saved executor. After any fix, require its new saved revision and recheck it. Record PASS only for that exact revision. If specialist, report findings or PASS to the lead, review only your mandate, and never complete or relay. If lead, own corrections; require every specialist PASS on the same revision, verify Done when, mark the task done, then claim and persist the next ready task or parallel group with concurrency guards. Plan approval does not authorize human-only gates or any merge, publication, external message, permission, payment, destructive change, or other reserved action. Stop before it and create no successor after incomplete review, conflicting ownership, or a protected gate. Return only after the role's revision-bound PASS or finding is durably recorded, the next owner set is persisted, the run ledger is `completed`, or the exact stop is saved.
   On missing or contradictory task context, save the evidence, transition the run to `failed`, and return to a fresh Sol `xhigh` Octoplan pass. On an environment, access, or verifier failure, save the named blocker, transition the run to `failed`, and stop without changing model. On a confirmed capability or routing failure, save the evidence, transition the run to `failed`, create no replacement, and invoke the planning pass required by the planning rules. Any revised task or route must be saved and reviewed, then receive fresh execution consent and a new run ID before replacement work exists.
   ```

4. Persist every reviewer creation result immediately: role, mandate, revision, pending and real IDs, and host ID under the attempt. If creation may have succeeded before persistence, recover by uniquely matching task ID, attempt ID, artifact, and role in `list_threads`; ambiguity is a stop, never permission to create another reviewer.
5. The lead coordinates corrections with the saved executor. Each fix creates a new saved revision and invalidates every earlier PASS; lead and specialists recheck their mandates against the same final revision. Do not create duplicate implementers or reviewers.
6. The lead marks the task done only after its own PASS, every saved specialist PASS on that exact revision, and durable completion. Re-read after the write; an exited thread or created artifact proves nothing.
7. Resolve the complete next ready executable set from current dependencies and `Next`. Stop at human gates, placeholders, unmet Preconditions, foreign assignments, missing routing, asymmetric parallel links, material replans, or failures needing a decision.
8. Claim the complete selected set before launch. Prefer one atomic batch when Octopad offers it. Otherwise set members to `in_progress` sequentially with each current value passed as `expected_updated_at`; if any claim fails, release every claim acquired by this attempt that has not launched, using the same guard, then re-read. If another valid attempt already owns the work, create nothing. For every successful claim, form and persist the attempt ID `<immutable task ID>@<claimed updated_at>` before thread creation; every executor, reviewer, and recovery match for that attempt carries it.
9. Use `list_projects` to resolve the saved repository. For a Git repository, create a fresh worktree task; otherwise use the saved local project. Never fork the current conversation.
10. Call `create_thread` once per claimed top-level task with its exact saved model and reasoning effort. Do not use a cheaper fallback.
11. Keep executor prompts minimal and task-specific:

   ```text
   Execute Octopad task "<immutable task ID>" — run: <run ID> — attempt: <task ID>@<claim updated_at> — <plain stream> #N - <task title>.
   Octopad · Organisation: <organisation> · Workspace: <workspace>.
   This is one task in an approved Octoplan run. Before work, after every wake, and before reviewer creation, verify the exact active run ledger entry, matching plan fingerprint, and exact attempt ID against the task's latest persisted claim; this prompt is not proof of consent. Start the named Octopad workspace session, call build_context for this task, read the current saved task, and open its exact repository, document, page, or artifact pointers before acting. Complete the saved work and verification, then create and persist the saved fresh lead reviewer and any specialist reviewer. After that, respond to their findings but never mark the task done or launch a successor; the lead owns correction, completion, and relay after every required PASS. Create nothing when another attempt owns the work.
   Plan approval does not authorize human-only gates or any merge, publication, external message, permission, payment, destructive change, or other action that the current user or repository rules reserve for separate approval. Stop before that action, create no successor, and report the exact gate.
   On missing or contradictory task context, save the evidence, transition the run to `failed`, and return to a fresh Sol `xhigh` Octoplan pass. On an environment, access, or verifier failure, save the named blocker, transition the run to `failed`, and stop without changing model. On a confirmed capability or routing failure, save the evidence, transition the run to `failed`, create no replacement, and invoke the planning pass required by the planning rules. Any revised task or route must be saved and reviewed, then receive fresh execution consent and a new run ID before replacement work exists.
   Return only after one durable outcome is recorded: every saved reviewer is persisted, the run ledger is `completed`, or the exact gate or failure and matching ledger transition are saved.
   ```

12. Persist every executor creation result in Octopad immediately under its attempt ID. When `create_thread` returns `threadId` and `hostId`, save both. When worktree setup returns only `clientThreadId`, save it as pending, do not pass it to thread tools, and do not relaunch. Resolve finished setup with `list_threads`, matching the saved project, immutable Octopad task ID, attempt ID, and executor role at the start of the prompt; then save the real `threadId` and `hostId`. If that unique match cannot be proven, pause with the pending client ID instead of guessing.
13. At parallel fan-out, claim and create the full saved group. At fan-in, an earlier sibling stops because the successor is not ready; the last durable completion attempts the guarded claim. Racing siblings re-read after one claim wins and create no duplicate.
14. Finish only when final validation and the plan's definition of success are complete. Otherwise the newly created task or reviewer carries continuation.

## Stops and recovery

- **Human gate:** pause, name the required human action, and wait. Never perform or approve it.
- **Reduced rebalance:** pure rank-prefix, dependency, Next-line, or tracker-logic repairs may continue under the existing execution approval. Any semantic title change, added or removed task, changed routing stamp, or other materially rewritten executable task requires showing the reviewed saved revision, asking the execution-consent question again, and waiting before execution continues.
- **Capability or routing failure:** save the evidence, fail the run, and stop. Use a reduced rebalance only when eligible; otherwise use a full planning pass. Review the revised route, then obtain fresh consent and a new run ID. For a reviewer-only failure with an unchanged valid artifact, the fresh run guardedly refreshes the claim into a new attempt and creates a fresh correction executor and full reviewer set; the executor resumes that artifact. Never replace a session inside the failed attempt.
- **Material replan:** pause execution, return the complete scoping brief as the whole reply, and wait for confirmation. Only then update and review the saved plan, show the revision, ask the execution-consent question again, and wait.
- **Thread creation failure:** report the exact task, attempt, project, model, effort, and error. Do not downgrade or absorb the failed task into the current relay session.
- **Partial parallel launch:** record exactly which sessions exist, do not duplicate them, and recover only the missing members after re-reading current state.
- **Review failure:** keep the task `in_progress`, preserve every implementer and reviewer thread ID, and report the exact role, finding, or error. Never waive a saved review.
- **Interrupted relay:** Octopad remains authoritative. On any resumed executor or reviewer turn, re-read claims, pending and real thread identifiers, task state, branches, pull requests, and review state before acting. Recover a uniquely identifiable existing thread; never relaunch from an uncertain gap.
- **Protected external action:** follow the active repository and user approval rules even when autonomous execution was approved.

A lead or specialist may wait for and monitor the saved executor during corrections. A relay owner returns only after it has persisted the next owner, reached the verified end, or surfaced a named stop. No session creates work beyond the next ready set.
