# The planning pass — the eleven steps

Load this when the resume check in SKILL.md says the invocation is a planning pass, and run the steps in order. Every rule in SKILL.md binds throughout — the non-negotiables, the simplicity bar, the task template, and the per-task self-check are there, not repeated here.

## Stream-type lenses (steps 1, 2 & 7)

One Octoplan for every domain — but the interview questions, the brief's assumption hunt, and the How/Verify slots take the stream's own best practices. A lens is a checklist of questions, not extra process: if a lens question has an obvious answer in the stream's source of truth, verify it there instead of asking the user.

- **Engineering.** Settle before planning: what merged-and-deployed behavior defines success; how it will be proven (which test suite, what new test); whether the data model changes (a migration is always a recorded Decision, and never runs in parallel with anything); what permission, security, or auth surface it touches (always recommend a review); how it rolls back if it breaks.
- **Content / marketing.** Ground in the governing canon (positioning, voice, channel history); settle the measurable outcome, the distribution channel, and who approves before publish. Publishing is outward-facing — the approval gate is a wired task in the plan, never an afterthought.
- **Ops / finance / legal.** Settle the source documents, the hard deadlines (dates written as absolutes, never "next month"), and the audit trail — every figure traceable to a named document.

## The multi-stream cut test (run in step 1)

When a request is too big for one work stream, plan it as ONE effort across several autonomous streams (Blueprint). Two signals decide the cut — either means cut: the definition of success only reads as several independent successes; or the work spans domains with different owners (an engineering half and a content half, say), each side holding 3+ tasks' worth of work of its own. A third is grounds to hunt for a real seam, never a cut by itself: the confirmed brief already names ~15+ distinct executable jobs. Sharing no files is a parallelism fact, not a seam — parallel groups inside one stream already cover it. Run this test in step 1, before the brief is drafted — the invocation names one stream, and that framing must not decide the shape.

If the test fires, load `references/multi-stream.md` and plan the effort by it: one effort-level scoping brief, the cut into streams, one light Blueprint page, optional per-stream sub-planners, and one supervisor per stream at delivery. If one work stream suffices, none of it applies.

## Steps, in order

1. **Review or discover.** Read everything that exists: the stream's tracker, every task, linked design pages, prior Decisions. A loose plan exists → review and improve it. The stream is thin or empty → interview the user first (purpose, scope, constraints, who it serves — one theme at a time), letting the stream-type lens shape the questions; the answers feed the scoping brief (step 2), and the design page and proposed task breakdown come only after the brief is confirmed. Also settle three practical facts you'll need later: which AI models and reasoning-depth settings the team's environment offers (for Exec recommendations), whether per-lane agent definitions exist there (one agent file per rubric lane, pinning model and effort together — see `references/routing.md`), and who on the team owns each human gate. A request that might exceed one stream runs the cut test above now, before the brief is drafted.
2. **Scoping brief — reflect back, then wait.** A stream whose tracker already carries a confirmed brief's content (its Scope, Rationale, and Definition of Success sections, written at step 10) re-plays only the delta: name what changed since those sections were written and confirm it; nothing changed → say so in one line and move on — an unchanged confirmed brief is never re-asked, and the tracker stays the single durable home of the brief. **The delta path may skip re-confirming scope. It may never skip the Readings**: a session planning against a document it did not write plays back its own reading of the ambiguous points once — the corpus, the comparison, what the deliverable actually is — however complete the tracker looks. The test is per-session, not per-document: "has the document changed" and "has this session confirmed its reading" are different questions, and the second is the one a complete-looking plan silences. Before locking any decision, drafting any design page, or writing any task, merge what the user said with what the sources hold and hand it back as ONE short brief in the chat, under the Brief banner (SKILL.md, One program). Scale it to the request — half a page for a rich stream, a few lines and a one-word confirm for a clear bounded one — but never skip it: the playback is the user's one guaranteed look at what the planner understood — a stream that already looks fully specced is where an unchecked misreading survives longest. The brief is the ENTIRE message: no decision proposals, no draft breakdown riding along — end the turn on it. Six parts, each present every time a brief is played back (the delta path above replays only what changed, Readings always included), with the stream-type lens shaping what belongs in each:
   - **Understanding** — the stream's purpose and deliverable, restated in the planner's own words.
   - **In / out of scope** — both lists explicit. An empty "out" list is a red flag: name at least the nearest adjacent thing the stream does NOT deliver.
   - **Success** — the definition of success the planner intends to plan against.
   - **Assumptions** — every point the planner settled by inference instead of a source or the user's words, one line each, with where the inference came from. An empty list must show its work: name where each usual hiding place (scope edges, audience, ordering, quality bar) was settled — a source read this session, or the user's words.
   - **Readings** — for everything the user named ambiguously (a source, a standard, a target, a corpus), how the planner has read those words, in its own words, with the rejected reading beside it where one is plausible: "I read the Nakamate org as data to copy into the rig — not as inspiration for writing the prompts." The verified-facts rule covers file paths and commands; this is its counterpart for the user's intent, and it costs one line per reading where an unchecked misreading costs the stream.
   - **Open questions** — what the planner cannot settle alone.
   Then STOP. Confirmation is a reply the user sends AFTER seeing the brief — no launch prompt, prior chat, or tracker note counts, however complete it looks. The reply confirms the brief as corrected: a correction replaces the assumption, and anything the reply leaves unanswered never defaults to the planner's assumption — re-ask once, then whatever stays open becomes a logged Question with its affected tasks as flesh-out placeholders. Do not start step 3 until that reply has arrived. (On the delta path's nothing-changed outcome the scope half needs no reply — the standing confirmation carries. The Readings always need one: play them back and wait for the reply before step 3, however complete the tracker looks.) The brief itself is a chat message, not an Octopad artifact — its confirmed content flows into Decisions, Questions, and the tracker, which are the durable records. A multi-stream effort writes ONE effort-level brief (see `references/multi-stream.md`).
3. **Delivery groundwork — settle it and record it; ask nothing here.** The brief settled WHAT the stream delivers; this settles HOW, and the planner settles it alone: between the brief confirmation and the finished plan the user is interrupted only by step 4's decisions — the calls only they can own. First read the target the work lands in — the repository, site, or workspace — and its own rule files: a `CLAUDE.md`, an `AGENTS.md`, or whatever house rules the team keeps there. Read them at this moment, not from memory. **Whatever those rules lock is a floor this session cannot lower, in every delivery mode.** The staging-first and reversible-by-design floors (SKILL.md, Non-negotiables) apply from groundwork on. Then settle and record as Decisions on the stream:
   - **Gate map — two labeled classes, never mixed.** **Person-waits:** every point routed to a named person — those the target's own rules route there, and those only a person can perform (an access to grant, a secret to paste) — honored in every delivery mode, consumed by nothing. **Protected effects:** every effect the plan will cause that consent must cover — data-schema or migration work, permission, auth, and security surfaces, publishing, deploying, deleting data, any step that bills money to any party (spend is protected even where no house rule says so), and anything else that cannot be undone. Protected effects are disclosed at the hand-off and consumed by the go. Name every entry with its owner (person-waits) or its consequence (protected effects).
   - **Reviewer routing** — which named person clears which class of task, and which classes are cleared by machine checks alone. Name a person only where an effective rule or the user's own instruction requires one: Octoplan never invents a human wait the team's rules don't impose.
   - **Stacking** — whether dependent changes stack on each other's branches as they go, or each waits for the previous one to land. Pick what the target's conventions favor.
   - **The full path to the finished state, accesses included.** Map what the delivery itself will need to reach Done — not just what the code needs: every environment, credential, secret, account, seat, and remote surface (a deploy, an infrastructure setting, a migration to apply) on the way from first task to finished state. (The consent side of those effects is the gate map's protected-effects class above; this map owns reachability — who can reach each surface, with what credential.) Anything only a person can provide — a secret to paste, an access to grant — becomes a human-only task wired BEFORE its dependents, entered in the gate map's person-wait class, so it appears in the hand-off's plan list and is asked at the go, never discovered mid-run with the stream stalled behind it. An ask the plan makes at the go costs the user one moment they are already spending; the same ask at delivery hour nine costs a stalled run. And prove each remote surface's reachability and permission shape before the go — a read or a dry call against the code host, the CI, the messaging channel, the deploy target — never the protected effect itself: a surface that turns out unreachable is a plan fact to wire now, not a discovery to make after the branch work is done.
   - **Stakes and the kill question** — one Decision naming the decision this stream feeds, its blast radius, whether a wrong outcome can be undone, and the stream's kill question: the one assumption that makes the whole output worthless if wrong, stated falsifiably with the observation that would show it ("worthless if the two arms differ in anything but the methodology text — shown by any input one arm receives and the other does not"). This record is what sizes every review floor and Verify slot (SKILL.md, Non-negotiables), and what every later session re-answers.
   A genuine alternative only the user can own — one with real consequence trade-offs the sources cannot settle — is not asked here either: it goes through step 4's decision shape with everything else. **These recorded Decisions are the stream's delivery contract, and it lives in Octopad, never in this chat:** a worker session, or any session that resumes this stream later, reads its mandate from those Decisions and from nowhere else. The delivery mode — how much the user wants to be interrupted — is asked ONCE, at the hand-off (step 11), where they can see the finished plan it applies to.
4. **Lock decisions.** Surface every open call and present each in this shape before locking: **Deciding** (what and why it matters, in real-world terms) → **Options** (each with what you gain and what you give up) → **Recommendation** (your pick and why) → **Reversibility** (how hard to undo). Confirm ONE decision at a time — a "go ahead" locks only the item just confirmed, never neighboring proposals. A call the user already settled in the brief reply is recorded as a Decision directly, not re-presented. Record each as a Decision on the stream. Three format rules, because the record is what every later session checks against:
   - A Decision that fixes an **interpretation of something the user said** records the rejected reading in the same sentence: "Corpus: clone Nakamate as seed data — NOT: use it as inspiration for writing the prompts." Without the excluded reading, the chosen one reads as the user's settled fact to every later session, and nobody re-asks.
   - A Decision that **constrains a rig, an experiment, or any built artifact** states its own observable test — "an arm is correctly blinded when X is observable and Y is not" — so that retiring it later has something concrete to sweep against (SKILL.md, Replanning).
   - Where a Decision's content exceeds Octopad's field size, **write the full record on a linked page and make the Decision the pointer** — planned from the start, never discovered at the cap by deleting reasoning until it fits. The reasoning trimmed to fit a field is exactly the part a later session cannot reconstruct.
5. **Plan hygiene + execution order.** Close done-but-open tasks; align the stream's definition of success with real scope — **and make it countable: the definition of success contains at least one number, and every count a task spec carries (16 pairs, 3 posts, 40 records) appears in it too, so amending one amends both**; a definition made only of properties gives the delivery report nothing to measure distance against. Log open Questions. Then wire the order so "what's next" is never ambiguous:
   - **Dependencies are the machine-readable order.** Wire a dependency edge (with its one-line rationale) for every real "B needs A" relation — edges work across work streams in the same workspace. Octopad's next-task resolution skips tasks whose dependencies aren't done.
   - **Title prefix is the human-readable order.** Name every executable task `#N - <title>`, N being its rank among the stream's executable tasks. The rank shows in every task list and in the continuation prompt.
   - **A Next line closes every executable task's description** — the hand-off instruction the finishing session follows. Write it using the exact patterns in `references/continuation.md` (load it now if it is not already loaded); it is the only way the chain moves.
   - Add the **final validation task** — whatever proves the stream's definition of success (an end-to-end test for a build stream, a publish-readiness review for a content stream), wired after the delivery tasks, with one subtask per check. Its checks exercise the real produced path end to end — a check that hand-feeds the intermediate state production is supposed to derive proves nothing about the joints between tasks. Producing a manual checklist for the user is part of its Done when. Where the stream ships behavior a user or the team will see, one subtask confirms the documentation consequence is recorded in the target's own mechanism (for a repository, its per-change doc-impact convention), or a Decision records why none is needed.
   - **Add a landing task wherever the finish line is out of reach.** Where the target's rules stop this session short of the finished state — a change it may not merge, a draft it may not publish — the step that finishes the job becomes ONE human-only landing task, owned by the named person, wired last: it **depends on** the final validation task, which depends on the delivery tasks. Each delivery task's Done when is then the state it can actually reach — open, checks green, handed off — and the stream ends on the landing task. Skip this and the board reads delivered while nothing has shipped, with the step that decides whether it did nowhere on it.
   - **One owner per piece of user-facing text.** Where the plan holds a task scoped to write or rewrite wording a user will read, no earlier task may invent text inside that scope: it either writes the final wording against a standard locked as a Decision, or leaves it blank for the owning task. Two tasks writing the same sentence is rework the planner authored, and it costs twice again in every translation.
   - **Human-only tasks** (approvals, access grants, landing the work) get no `#N` prefix, no Exec/Review lines, and no Next line — dependencies gate them, and the preceding executable task's Next line carries the resume instruction (see `references/continuation.md`). They still need Why, What, Done when, and the impact parameters like any task, and are assigned to the team member who owns the action.
6. **Ground in reality + runnability.** Engineering streams: map the repository's real conventions with read-only exploration; anything written into a spec must be confirmed by a direct read. Business/content streams: ground in the governing documents instead — read them IN FULL plus the live external surfaces; never spec from memory. If the planner itself lacks access to a governing surface, log a Question and mark the affected tasks as flesh-out placeholders rather than speccing blind. All streams: confirm every Verify step is executable with access that exists today. Three triggers say a step is not runnable as written: it needs a login, it needs a seat on a third-party product, or it needs a browser the executor cannot drive. Then wire the remedy per step 3's access map: access an agent can obtain itself becomes its own ordinary task wired before its dependents; access only a person can grant or exercise becomes a human-only task with a named owner, in the gate map's person-wait class, and no Verify line at all. Settle in step 1 what the executor can and cannot drive, or the third trigger is unanswerable. A check that can only mature later (a metric measured weeks after delivery) is not a runnability failure: name the event or date it waits on in a `**Preconditions:**` line. Any spec that assumes prior work is LIVE (deployed / published), not merely written, also gets a `**Preconditions:**` line naming what must be live first. And where only a person can make that state true (a migration applied, a deploy run, an approval given), the line alone is not enough: wire the wait as a human-only task with a dependency edge, so it lives in the graph Octopad resolves next tasks from. A wait recorded only in prose is invisible to the machine order, and it resurfaces later as a supervisor's guess about what may proceed — the graph, not anyone's reasoning, is what says a task waits.

   **Runnability is half of this step. Validity is the other half:** runnability asks whether every Verify step can be executed; validity asks whether all of them, passing, would establish the stream's claim — a rig can pass every internal check and still be unable to answer its own question. Two rules for any task that builds an experiment, a staging reproduction, a fixture environment, or a simulation:
   - **A parity manifest, built outward-in.** Start from the real system the rig stands in for and enumerate every input a real session or user receives there — files on disk, tool names and descriptions, instructions, account and environment state — then state, per row, what the rig does. Enumerate from the real system first, before reading the rig's design notes: the rig author's own account of what varies lists only the differences already considered legitimate, and has already stated a fatal difference as the design. Every row where the rig differs and the difference is not the declared variable under test is a defect, not a design note — and the declared variable itself is justified, never asserted: one line proving it is exactly what the stream's question needs varied, because a row accepted on the strength of the word "intended" in its own file is the fatal case, not the safe one. And **closing any parity defect requires producing the full manifest, not just the repair** — a fix that names one row and closes is refused the way a claim without evidence is, because the found instance otherwise becomes the definition of the problem.
   - **A rehearsal before the spend.** Where a task's output is a run whose cost is material — many sessions, metered spend, wall-clock hours — its Verify slot carries the smallest end-to-end execution that would exhibit the run's core premise, with the pass condition stated in advance and the result reported before the full run is dispatched. **The result binds:** a rehearsal that fails its stated pass condition stops the full run's dispatch and routes through Replanning or the user — never into "log it and keep going", which is how a run that had already announced its own worthlessness got fifty more sessions. Spend a few percent of the budget to learn whether the rest can produce an answer at all; a premise checked after the run is a post-mortem.
7. **Spec into tasks — fill the template.** Write every executable task with the template in SKILL.md, every required slot filled before saving. Load `references/routing.md` before writing Exec and Review lines. Implementation-grade detail goes INTO the description — exact paths or source documents, the outcome and the constraint the work must satisfy, edge cases, and the exact verify steps (precise commands or concrete checks, not "run the tests" — the executor has no memory of any chat and can't infer them). The How must call for the simplest implementation that fully solves the job — reuse existing functions, templates, and patterns before adding new ones; simple, complete, and matching the surrounding conventions beats clever. State the outcome and the constraint; dictate a technique only where a real trap needs naming, and then say why. Name an existing thing as the precedent to copy only where this session checked that the precedent carries — an element's look, a mechanism's behaviour, a claim's truth — because a precedent named without that check hands the worker a defect nobody measured. A task that can't be fully specced yet (it depends on another task's output) is a **placeholder**: it keeps its `#N - ` title AND the required Why / What / Done when headers and impact parameters (or the create is rejected), but each body slot holds one line only, with this note as the What: "⚠️ Octoplan flesh-out required: run an Octoplan pass before building, because <what is missing>" — an executor reading it flags the user instead of building on a placeholder.
8. **Self-check gate.** After all tasks are written, walk every task against the per-task self-check in SKILL.md (re-read each FROM OCTOPAD — what was actually saved, not what you remember writing), then walk the whole plan against the per-plan list below. Fix failures on the spot, then re-check the fixed task.
9. **Adversarial review — never skip, sized to risk.** At least ONE fresh-eyes agent attacks every plan — that floor never moves; a plan of 8+ tasks, or one touching data migrations, permissions or auth, privacy, money, publishing or deploying, or destructive operations, gets 2+ reviewers, each carrying ONE lens. The task-count trigger alone yields to the stakes Decision — a reversible, internal 8+ plan may stay at one reviewer, saying so; the named risk categories never yield. And wherever the stakes Decision lowered a floor, the remaining reviewer's mandate includes the stakes record itself: is this outcome really reversible and internal? Reviewers attack the plan against the real source of truth — the repository for engineering, the governing documents and live surfaces for content — worst problems first. Give each reviewer the verbatim saved task text (fetched from Octopad, never your summary) plus access to that source, and have it verify claims with its own reads. Where one reviewer covers the whole plan it runs lenses (a) and (b) together; with 2+, assign each agent one: (a) **design soundness** — is this the right plan; wrong decomposition, missing decision, simpler structure available, and does every spec match the confirmed scoping brief, corrections included; (b) **executability** — can a memory-less session complete each task from its spec alone; paths real, steps runnable, dependencies and Next lines correct, and the artifact graph closes per the per-plan self-check's artifact rows (every produced artifact has a named consumer and producer in production; every deferral mirrored in its target's spec). On the 2+ plans above, add a third lens: (c) **risk** — what breaks, what loses data, what needs a human sign-off the plan doesn't flag — including any protected effect the hand-off message fails to disclose, because the go the user gives covers only what that message shows. A plan whose deliverable is a measurement, a comparison, a score, or a verdict always adds the **premise** lens from `references/routing.md`, pointed at the planned instrument: would this apparatus, working exactly as designed, measure what the stream claims to measure, and would a plausible alternative explanation produce the same result? A finding may be dismissed only by verifying the contrary in this session's tool output — otherwise fix the specs or log a Question. The reviewers' packet also lists, explicitly, every product-behavior claim the plan pins into user-facing wording or a Decision, and every claim about what the environment can or cannot reach — named claims get attacked and verified; unnamed ones are the false premises that survive every general verify-everything rule.
10. **Write the plan's logic into the stream tracker.** Every work stream has a tracker page carrying the sections the planner owns (Scope, Rationale, Definition of Success) alongside the system-generated Progress Report and Activity Log. Update it so the ordering makes sense to anyone opening the stream later: **why the tasks run in this order**, which branches are parallel and why they are safe to split, where a human gate sits, and what ends the stream. Keep it short and keep it logic-only — no task statuses, no copies of task content, nothing the task graph already holds, or it goes stale the first time work moves. This is the same job the Blueprint page does for a multi-stream effort, at single-stream scale. Never hand-write the Progress Report or the Activity Log; the system owns those.
11. **Hand off.** Rename the work stream so its name ends with ` (octoplanned)` — skip if it already does — so anyone scanning the workspace sees which streams have been through a full Octoplan pass. The suffix is a marker for humans reading the workspace, not part of the stream's identity: continuation prompts always use the plain name. Then end with the hand-off message, under the Plan banner (SKILL.md, One program), in this fixed order every time, so the user recognizes the moment across streams. Do NOT restate chain state or the team's standing rules in it: state lives in Octopad, rules live in the team's own instruction files. If you're tempted to add a fact to the handoff, it belongs in an Octopad task, Decision, or knowledge item — put it there.
    1. **The plan, shown.** One line per step, in execution order: every task's title restated in plain words, and every step a person performs in bold with its owner named — `**Human — <owner>: gives the final approval to publish.**` Every protected effect the plan will cause is disclosed here in bold consequence words on the line of the step that causes it — `**changes the database's structure**`, `**deletes existing records**`, `**spends money on X**`, `**publishes to Y**` — because the go the user gives authorizes exactly what this list shows, and nothing it does not show. An irreversible effect outside every named category is still disclosed: anything that cannot be undone belongs in bold. **A disclosed effect that touches a shared resource carries its magnitude in the same line** — how many times, how much data, which shared system: "**restores ~400 rows into the shared staging database, 32 times**", never "repeatedly refills two test organisations" — because the user answers the sentence they are shown, and only the quantified one is the truth. The same bold lines are the marked points: under the Checkpoints mode, delivery pauses at every bolded step — each human step, protected effect, and landing. Titles and owners are the plan's shape, not its state — statuses and specs stay in Octopad, so this list does not breach the no-chain-state rule above. Under the list, name every open Question and every flesh-out placeholder the plan still carries; if there are none, say so. The user approves what this message shows them, known unknowns included, so never ask for a go on a plan the message does not show; a task count is not a plan.
    2. **The delivery terms, stated as settled.** A few lines under three headings — *What needs a person's OK* · *Who checks the work* · *Does dependent work wait?* — reconciled against the tasks as actually specced (the groundwork in step 3 was recorded before they existed). Where the stakes Decision sized the review down, *Who checks the work* says so in plain words — "nothing here can't be undone, so each task gets one fresh check rather than two" — because the user corrects what they can see, and a silently lowered floor is a call they never got to own. State them as settled facts the user may correct, never as questions: a choice with one possible answer spends the only attention the message gets. Update the contract Decisions with any correction.
    3. **The delivery offer.** Say who should now supervise delivery — this session or a fresh one — and for a fresh one, name the model and reasoning effort the supervisor session should run at (the supervisor checks the plan's work, so its route is never cheaper than the strongest Exec route saved in the plan), and whether it runs solo or is safe to run alongside other work on the stream. Judge your own remaining context before you offer: verification — reading each change and each reviewer's findings — is what spends the budget. Recommend a fresh supervisor whenever the planning pass was heavy (substantial review findings, a replan, a long exploration); when in doubt, hand off — one paste for the user beats a stream stalled mid-flight. Supervising from here suits a light pass on a short plan.
    4. **The outcome, and its kill question — two lines, directly above the question.** What the stream produces, in the countable units of its definition of success ("16 paired comparisons and a verdict"), and the one assumption that makes it worthless if wrong ("worthless if the two arms differ in anything but the methodology text"), from the stakes Decision — ending with an explicit invitation: if that assumption is wrong, saying so now outranks any mode choice. The disclosure list above answers *what does this cost me*; these two lines answer *what am I getting, and how could it be nothing* — and this is the single moment the user is maximally engaged and holds domain knowledge no planner has, so it is where the wrong premise is cheapest to catch.
    5. **The one question, always bold and always last before the block** — the delivery mode and the go are a single answer: `**How should I deliver this? Full autonomy — I run the whole plan above, including the consequences it discloses, and report when it's done · Checkpoints — I also pause at each step shown in bold above · Step-by-step — I pause after every task. Name one and it's your go: I record it as your permission and delivery starts.**` Recommend one mode in the line above the question, with its trade-off in a few words, and add one plain line that the user may instead leave the plan waiting (without a go it sits in Octopad, and the continuation prompt is how it moves later) or run the tasks by hand one at a time — a hand-run choice is a go like any other: record it, naming step-by-step as its mode and no supervisor route. The user may also strike or add marked points in their answer — the go Decision records the final set. The answer is the user's sign-off on the reviewed plan THIS message shows, disclosed consequences included; once recorded it is the stored permission every later session reads instead of re-asking. In full autonomy nothing the plan disclosed interrupts them again — the next thing they hear is progress, or a genuinely new fact asking new consent.
    6. **The prompt block for the recommended path**, with its settings line (model · effort · solo or parallel-safe) under it, per `references/continuation.md`. A multi-stream effort emits one supervisor block per stream instead (see `references/multi-stream.md`). Fresh supervisor recommended → the supervisor handoff block, told plainly to paste it only after the go is recorded (the receiving session checks for the recorded go and only re-runs planning without it). This session supervising → no block; say the go starts delivery right here. User chose the manual task-by-task path → the first ready task's block instead.
    **A go is an answer to THIS message.** A go typed before the hand-off was shown — in the invocation, in a queued line, in prior chat, however unambiguous it sounds — is not a go: show the plan and ask the one question anyway, because what the go authorizes is exactly what the message shows, and a consent that predates the disclosure covers nothing. This is not a second ask for the same thing: the invocation asked for the planning; this question is the sign-off on the plan it produced. The go Decision therefore never predates the hand-off message it records, and it names which message the go answered. On the user's explicit go, first record the go itself as a Decision on the stream — on every stream, for a multi-stream effort — naming the chosen delivery mode, copying the hand-off plan list's bold lines into it verbatim (the disclosed effects and marked points — the only test a later session has of what the go covers; on a multi-stream effort each stream's Decision copies only its own stream's bold lines), and naming the reviewed graph: every task's stable ID (with its `#N` rank where it has one — human-only tasks have none and belong in the record too) and its last-edit timestamp as read AFTER the review's fixes. Where this exceeds the Decision's size, put the full record on one linked `Go record — <stream>` page and let the Decision point there — and record the supervisor route (model · effort, solo or parallel-safe) in that same Decision, because the delivery offer exists only in this chat and a replacement supervisor must find its route in Octopad. That record is what lets a later session know it may resume, and it is what makes handing off safe: the fresh supervisor reads the go as permission already given and never asks for it again. Then either load `references/supervision.md` and follow it, or end with the supervisor handoff block. Without a go, nothing else happens here: the plan sits in Octopad and the continuation prompt is how it moves.

## Per-plan self-check (step 8, after the per-task list)

- The scoping brief was confirmed by a user reply sent after seeing it, before any decision was locked or task written; every assumption in it was confirmed, corrected, or logged as a Question.
- The delivery groundwork is recorded as stream Decisions — the gate map, the reviewer routing, the stacking choice, and (once the go arrives) the delivery mode inside the go Decision — with nothing load-bearing left only in the chat.
