# Multi-stream efforts (Blueprint)

Load this when the cut test in `references/planning.md` fires, and whenever you rebalance or supervise a stream that belongs to a multi-stream effort. An effort is a goal + several work streams + one Blueprint page, all in the same workspace (dependency edges cannot cross workspaces) — no new Octopad object is needed.

The scoping brief (`references/planning.md`, step 2) is written ONCE for the whole effort, before the cut into streams — the assumptions worth catching (where the seams fall, what each stream owns) live at effort level. A later Octoplan pass on a single stream of an existing effort writes its own stream-level brief: the effort brief covered the cut, not the stream's internals.

1. **Cut the work into autonomous packages**, one work stream each. A package stays a top-level task of its own stream — never artificially demoted to a subtask of another stream's task. Link every stream to the same goal. Wire the real dependencies between tasks across streams and note what can run in parallel.
2. **Write one Blueprint page** — deliberately light: the expected outcome, each stream's role, the global order, the parallel branches, the few dependencies that matter, the human validation points, and the effort's end condition. Link it to the tasks it governs so every executor immediately sees where its work sits in the whole. The Blueprint explains the logic; the Octopad dependency graph enforces it — the page carries no statuses and no copies of task content, so it never goes stale.
3. **Plan at effort scale.** Continuation crosses stream boundaries like any other step: a task's Next line may point into another stream — the continuation prompt then names that stream. The effort's final validation task includes one closing subtask: **archive the Blueprint page** once the effort is done.
4. **Plan the streams with sub-planners — where the environment can fork subagents.** After the effort brief is confirmed and the Blueprint is written, the master planner may spawn one planner subagent per stream instead of planning every stream itself. Fork each sub-planner so it inherits this session's full conversation — the confirmed brief, the sources read, the Blueprint's reasoning arrive with no re-briefing — and give it one stream and one boundary: run Steps 4–8 and 10 of `references/planning.md` for that stream against the Blueprint as written, with two carve-outs. Any question touching a seam — anything two streams share — comes back to the master and is never settled unilaterally. And any choice between real alternatives that needs the user comes back too: the master presents it in Step 4's shape and records the Decision, because a sub-planner never addresses the user — the master owns the chat and every user gate, and the effort-level brief and contract stay the master's. The master then wires the cross-stream dependency edges, runs the effort-level adversarial review (Step 9) over every stream's saved tasks, and owns the single hand-off. The fan-out buys speed and keeps the master's context free; it costs MORE tokens — each fork carries this conversation's whole history — so fork only while this session is still light, and prefer sequential planning or later per-stream Octoplan passes after a heavy exploration phase. A master dying mid-fan-out loses nothing: sub-planners save tasks, Decisions and Questions to Octopad as they go, streams with saved tasks stand, and each unplanned stream gets its own later Octoplan pass.
5. **Deliver with one supervisor per stream.** At the hand-off of a multi-stream effort:
   - **Every stream carries the full delivery record.** On the user's go, record the go Decision on EVERY stream of the effort — each carrying that stream's own supervisor route — copy the contract Decisions onto every stream, and rename every stream with the ` (octoplanned)` suffix. The resume check runs per stream: a stream missing any of this sends its supervisor back to planning, or back to the user for a go already given.
   - **One supervisor handoff block per stream**, each with its settings line, saying which streams are safe to start together — those with no undone cross-stream dependency between them. Octopad's readiness serializes the rest: a task whose dependency sits in another stream is simply not ready until that stream lands it.
   - **Shared landings are ordered in the graph, not in chat.** Where two streams land changes into the same repository or surface, the Blueprint names which stream lands first and the graph carries it — a cross-stream dependency edge or a human-only landing task (the landing-task rule in `references/planning.md`, step 5). This never moves the delivery mode, the gate map, or a landing task's named human owner.
   - **Rebalancing is per stream.** A supervisor rebalances only its own stream. A change touching a seam — a cross-stream dependency, the Blueprint's order, the effort's end condition — stops for the user, like any out-of-contract discovery (see Replanning in SKILL.md).
   - **Durable information crosses streams through Octopad, never through chat.** A discovery that matters to a sibling stream is written to the task or the stream's knowledge FIRST; where the environment lets sessions message each other, the message to the sibling supervisor is a nudge to go read it, never the record itself. Supervisors on a multi-stream effort re-read the Blueprint before their first task (see `references/supervision.md`).

## Effort self-check (feeds the per-plan self-check in `references/planning.md`)

- Blueprint page exists, is light, is linked, and its archiving is a closing subtask of the effort's final validation task.
- At the delivery go, every stream carries the contract Decisions, its own go Decision with its own supervisor route, and the ` (octoplanned)` suffix.
- Cross-stream dependencies are wired as edges; shared landings are ordered in the graph.
- No stream supervisor's territory crosses a seam.
